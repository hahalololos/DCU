# DCU + Qwen3.5-27B 推理服务优化调研总览

生成日期：2026-07-04

## 1. 调研结论摘要

本轮调研已完成赛题规则、公开模型配置、vLLM 0.18.1 评测口径、DCU/DTK 公开资料与第一批优化候选方向的整理。当前本地工作区只有赛题 Markdown/PDF 文件，未发现可运行的 vLLM、OpenCompass、HIP/DTK 或 DCU profiling 工具，因此 baseline 性能数据尚不能在本机实测，已在 `02-Baseline性能画像表.md` 中保留待填字段和采集流程。

当前最重要的判断：

1. 初赛核心目标是单卡、单请求、长上下文在线推理服务的输出吞吐提升。
2. SLA 是硬约束：任一档位 TTFT P99 或全局 TPOT P99 违反门限，该档吞吐得分清零。
3. 8k-16k 档位权重最高，为 50%，第一轮实验应优先服务该档，其次是 16k-32k。
4. 赛题明确允许 KV Cache 管理、执行路径、算子和推理期非持久化低精度优化。
5. 赛题明确禁止模型结构/权重/输出语义改变、投机解码、跳层、剪枝、预缓存测试集或可复用量化权重缓存。
6. 公开 `Qwen/Qwen3.5-27B` 配置显示其文本骨干为 64 层、24 attention heads、4 KV heads、head_dim 256，并采用 3:1 `linear_attention` / `full_attention` 混合层结构；KV Cache 估算必须区分 full attention 层和 linear attention 层状态。

## 4. 关键数据与估算

### Qwen3.5-27B 公开配置摘要

来源：`https://huggingface.co/Qwen/Qwen3.5-27B/raw/main/config.json`

| 字段 | 值 |
| --- | --- |
| `num_hidden_layers` | 64 |
| `hidden_size` | 5120 |
| `intermediate_size` | 17408 |
| `num_attention_heads` | 24 |
| `num_key_value_heads` | 4 |
| `head_dim` | 256 |
| `dtype` | bfloat16 |
| `max_position_embeddings` | 262144 |
| `full_attention_interval` | 4 |
| full attention 层数估算 | 16 |
| linear attention 层数估算 | 48 |

### KV Cache 粗略显存估算

只估算 full attention 层的 K/V cache，bf16 每元素 2 bytes：

```text
每 token KV bytes = full_attention_layers * 2(K,V) * num_kv_heads * head_dim * bytes_per_element
                 = 16 * 2 * 4 * 256 * 2
                 = 65,536 bytes/token = 64 KiB/token
```

如果把 64 层都按 full attention 保守估算：

```text
每 token KV bytes = 64 * 2 * 4 * 256 * 2
                 = 262,144 bytes/token = 256 KiB/token
```

| 上下文长度 | full attention 层 KV 估算 | 全 64 层 full attention 保守估算 |
| --- | ---: | ---: |
| 4k | 256 MiB | 1 GiB |
| 8k | 512 MiB | 2 GiB |
| 16k | 1 GiB | 4 GiB |
| 32k | 2 GiB | 8 GiB |

说明：linear attention 层通常不是传统随上下文线性增长的 KV Cache，但具体状态布局要以 vLLM 0.18.1 对 Qwen3.5 的实现为准。正式优化前必须读取评测容器内的模型适配代码和启动日志中的 KV cache size。

## 5. 第一轮建议实验方向

比赛方已提供 `testdata/` 样本和脚本，应以该目录中的官方样例口径作为第一轮实验入口：

| 脚本 | 作用 |
| --- | --- |
| `testdata/start_vllm.sh` | 启动 `Qwen3.5-27B` vLLM OpenAI-compatible 服务 |
| `testdata/run_throughput.sh` | 按 `4-8K`、`8-16K`、`16-32K` 三档运行 `vllm bench serve` |
| `testdata/run_accuracy.sh` | 使用 OpenCompass 跑 `hotpotqa`、`gov_report`、`retrieval_multi_point`、`aggregation_keyword_aggregation` |

建议优先做以下 3 个方向：

| 优先级 | 方向 | 理由 |
| --- | --- | --- |
| P0 | Decode full-attention / PagedAttention kernel 画像与优化 | 直接影响 TPOT P99 和输出吞吐，且长上下文下 KV 读取带宽压力最明显 |
| P0 | KV Cache block 管理、对齐、碎片和显存预算画像 | 赛题明确点名，风险低，能解释 16k-32k 显存与尾延迟问题 |
| P1 | 单请求执行路径与 Python 调度开销削减 | 并发固定为 1，很多通用调度路径可能变成 TTFT 固定开销 |

低精度方向如 KV Cache 量化、activation 动态量化、kernel 内临时转换建议作为 P1/P2，并且每次必须同时跑精度评测。
