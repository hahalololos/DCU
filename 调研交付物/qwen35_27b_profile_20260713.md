# Qwen3.5-27B 全链路 Profile 报告

时间：2026-07-13  
生产基线：`vllm_cscc@0adf0494e9bdc93a2fe4f9dd96a68f41e1869a73`

## 结论摘要

本轮已经完成三档 27B 热基线、三档 P50/P90 的 Prefill/Decode 配对 trace、两轮稳定性
复测、比赛权重加权，以及 Decode GEMM、UA2D、UA3D 的无计数器 micro 和 rocprof
硬件计数器采集。24 份配对 trace 全部满足输入、输出长度和生成前缀一致性门禁。

风险调整后的优化顺序为：

1. **Decode GEMM 结构优化**。它占比赛加权端到端时间约 `62.57%`，其中首先攻
   LLMM1 的 MLP gate-up，再攻 `F.linear` 的 MLP down 与 LM head。只要整个 Decode
   GEMM 提速 `10%`，理论端到端收益约 `5.69%`，是当前唯一有充分收益空间的主方向。
2. **UA2D 的 LDS/VGPR 结构优化**。它占加权端到端约 `10.34%`；长档 Prefill 中占
   `38.04%`。计数器显示 `256` 个 arch VGPR、`16 KiB` LDS 和约 `9.88e8` 次 LDS
   bank conflict。后续应改变数据布局、访存和归约结构，不再扫描已经淘汰的编译常量、
   `rows_per_block` 或 TILE64。
3. **UA3D 的 KV load/segments 探索**。主核 L2 命中率仅约 `1.37%`，同时使用
   `252` 个 arch VGPR 和 `16.5 KiB` LDS，符合 KV 流式读取受限特征。`reduce_segments`
   仅约 `0.082 ms/token`，不值得优先做 merge 融合。UA3D 总加权占比仅 `2.69%`，因此
   只能作为低成本探索项，未出现大幅 micro 收益前不进入服务 A/B。

GDN 虽占约 `3.64%`，但已有原型出现“micro 正收益、端到端回退”；GPU idle gap 总占比
约 `2.36%`，完全消除才有相近上限。两者本轮均暂缓。

最新榜单记录仍是第 8 次提交：排名 `62`，三档吞吐 `12.48/16.93/15.17`（16–32K、
4–8K、8–16K），最终得分 `81.6885`，精度与 SLA 扣分均为 0。本报告的 10 条 profile
基线用于热点分解，不是完整榜单复现，不能与榜单吞吐直接横向比较。

## 1. 测试范围与方法

### 1.1 环境与锁定参数

- 模型：容器本地 `/root/models/Qwen3.5-27B`。
- vLLM：editable location 指向
  `/public/home/acoh0h1o0p/DCU/vllm_cscc`，源码提交为 `0adf049`。
- 启动参数保持比赛约束：`max-model-len=32768`、`max-num-seqs=128`、
  `max-num-batched-tokens=4096`、BF16、单卡。
- 三档比赛权重：4–8K/8–16K/16–32K = `20%/50%/30%`。
- 共享目录已满，原始 trace 与 rocprof 数据保存在容器本地 `/root/profile27b/`。

### 1.2 Prefill/Decode 分离

每档先跑 10 条无 profiler 热基线，从成功且可生成至少 65 token 的请求中，选择输入长度
最接近 P50/P90 的样本。每个样本分别采集：

- 相同 prompt、temperature，`output=1`；
- 相同条件，`output=65`；
- 每组重复两轮；
- 以 `(trace65 - trace1) / 64` 估算稳定 Decode 每 token 成本。

每个 P50/P90 样本使用独立 vLLM 服务，只在该进程内完成一对 `o1+o65` 采集后退出。
最初尝试在同一服务中多次 start/stop ROCm Torch Profiler，在第 4 次调用时触发 HSA VM
fault；改成单样本隔离服务后，后续采集全部稳定完成。该故障只影响采集方法选择，没有纳入
任何性能结果。

### 1.3 有效性门禁

- 三档热基线均 `10/10` 完成、0 失败。
- 24 份 trace 对应的单请求均 1/1 完成、0 失败。
- 配对请求输入 token 数完全相同，输出严格为 1/65 token。
- 每个 65-token 文本均以前一个 1-token 文本开头。
- 两轮最大波动：Prefill kernel 时间 `0.216%`，Decode kernel 时间 `0.210%`。
- 无计数器 micro 的 UA2D、UA3D 均与对照 bitwise 一致。
- rocprof 注入会重放应用，其耗时只用于硬件瓶颈分类，不用于性能比较。

## 4. Decode GEMM 细分

稳定 Decode 的两个主要 Linear kernel 为：

| kernel | 时间/token | 调用/token |
| --- | ---: | ---: |
| LLMM1 | 34.333 ms | 176 |
| 其他 `F.linear`/Tensile | 14.642 ms | 129 |

LLMM1 的调用结构可由模型层数精确解释为 `48 + 48 + 16 + 64 = 176`：GDN qkvz、
GDN b/a、full-attention qkv+gate、MLP gate-up。无计数器 micro 折算如下：

| LLMM1 形状 | 单次 | 调用/token | 估算时间/token |
| --- | ---: | ---: | ---: |
| GDN qkvz `(16384,1,5120)` | 0.17710 ms | 48 | 8.501 ms |
| GDN b/a `(96,1,5120)` | 0.01263 ms | 48 | 0.606 ms |
| Attention qkv+gate `(14336,1,5120)` | 0.15606 ms | 16 | 2.497 ms |
| MLP gate-up `(34816,1,5120)` | 0.36373 ms | 64 | 23.279 ms |

因此 MLP gate-up 约占 LLMM1 时间的三分之二，按 trace 总 GEMM 归一后，粗略占整个
比赛加权端到端时间 `29.1%`。此前只调整 `rows_per_block` 最多仅得到约 `3.36%` 单形状
改善，说明下一步必须改变 LLMM1 的 load/reduction/vectorization 结构，而不是继续扫行块常量。

`F.linear` 的 `129` 次调用可解释为 `48 + 16 + 64 + 1`。其中已测得：

- MLP down `(5120,1,17408)`：`0.15245 ms`，64 次约 `9.76 ms/token`；
- LM head `(248320,1,5120)`：`1.90077 ms`，1 次约 `1.90 ms/token`；
- Attention out `(5120,1,6144)`：`0.05276 ms`，16 次约 `0.84 ms/token`。

MLP down 与 LM head 合计粗略占加权端到端 `14.6%`，应作为 Decode GEMM 的第二批
形状。现有隔离 Triton dot 原型对 MLP down 明显慢于 Tensile，不能沿用；应从 gfx936
专用 GEMV/skinny-GEMM 内核、权重访问合并和批量 launch 结构重新设计。

### 5.1 Decode GEMM

LLMM1 的 VGPR/LDS 占用不高，但 L2 命中仅约 `17.9%`，大量 wave 对同一 skinny-GEMM
权重流式读取，方向更接近内存访问效率、跨 wave 数据复用和减少调度开销，而不是进一步
降低寄存器。MLP down/LM head 的 Tensile 主核使用 `128` VGPR、`32 KiB` LDS、L2
命中约 `20%`；两者应分别针对高 K 和超大 M 设计，不能期待一个统一 tile 同时最优。

### 5.2 UA2D

UA2D 同时出现接近上限的 `256` VGPR、`16 KiB` LDS、非零 scratch，以及极高 LDS
bank conflict。后续优先验证：

1. 调整 LDS 中 Q/K/V staging 的维度顺序、padding 和每 lane 地址映射；
2. 缩短 live range、分阶段归约，降低 VGPR 峰值与 spill/scratch；
3. 在保持归约顺序和 bitwise/精度门禁的前提下合并连续 KV load；
4. 每次结构改动先做 8K/16K/32K micro，再做三档服务 A/B。

此前 `waves_per_eu`、MFMA 编译参数、TILE64 和纯常量扫描已被 micro 或端到端门禁淘汰，
不应重复投入。

### 5.3 UA3D

UA3D 主核几乎没有 L2 复用，且 VGPR/LDS 压力都高；这与每个 Decode token 扫描长 KV
上下文的行为一致。优先探索 segments 切分、KV 向量加载、block-table 连续区间快速路径，
并观察是否能减少主核读取量或提高有效并发。merge 核资源和耗时都很小，即使完全消除，
也只能节省约 `0.082 ms/token`，不应优先融合。

## 6. 推荐实施顺序与门禁

### 第一阶段：LLMM1 MLP gate-up

- 目标形状固定为 `(M=34816,N=1,K=5120)`，先做 gfx936 BF16 专用 micro。
- 需要至少 `5%` 单形状 micro 改善、P99 不回退、bitwise 或既定精度门禁通过。
- 结合 64 次/token 的真实调用结构评估，不接受只优化一次调用但增加额外 launch。
- 达标后先跑 4–8K 与 8–16K 端到端，再补 16–32K；三档文本和 token 数必须一致。

### 第二阶段：MLP down 与 LM head

- MLP down 优先级高于 LM head，因为其每 token 调用 64 次、累计约 `9.76 ms`。
- 分别建立精确形状 benchmark，避免用通用 GEMM 平均结果掩盖 skinny-GEMM 行为。
- 不复用已淘汰的通用 Triton dot 原型；候选需在当前 Tensile 基线上有明确收益。

### 第三阶段：UA2D 结构实验

- 只接受能解释计数器变化的结构实验，例如 LDS conflict、VGPR、FETCH_SIZE 明显下降。
- 目标至少 `1.24x` micro 提速，才有较大概率达到 2% 加权端到端收益门禁。
- 严格保持输入输出、模型语义、归约和比赛脚本约束；TILE64 曾改变生成轨迹，不能复用。

### 探索阶段：UA3D

- 先做低成本 segments/KV load 扫描；没有数量级改善不进入服务 A/B。
- 不优先处理 `reduce_segments`，不以 profiler 注入后的耗时判断性能。
